### 3. 診断: 潜在的な壊れ方だった

更新直後に最近のジャーナルを読んで気づき、両機の状態を非破壊で確認:

| 機体 | 稼働中 codex.exe | プロセス起動時刻 | 解釈 |
|---|---|---|---|
| masu-p55 | PID 26000 | 2026-05-22 04:21 | 私の更新より前 = **旧 0.130 が生存中** |
| しゅん先生 | PID 3960 | 2026-05-25 06:05 | 同上（更新の数十分前） |

- **npm 更新は on-disk バイナリだけ 0.133 に置換、メモリ上で動いている旧 0.130 プロセスはそのまま生存** → 今この瞬間は remote-control が動いている

- watchdog (`C:\ProgramData\codex-watchdog\`) ログ上、両機とも codex は頻繁に DOWN→UP を繰り返す運用
- → **次に codex が再起動した瞬間、watchdog が on-disk の 0.133 を起動 → Unix-only エラー → remote-control 停止**、という時限爆弾状態だった

## 学んだこと / 気づき

### 1. 🚨 Windows 機の codex 更新前に必ずピン留め判断を確認する

「3 台同様に最新化」は claude / gemini には当てはまるが、**codex だけは Windows ⇔ Unix で扱いが違う**。Windows は 0.131+ で remote-control が壊れるため 0.130 固定。`npm install -g @openai/codex@latest` を Windows で打つ前に、5/20 ジャーナルのピン留め判断を確認すべきだった。CLAUDE.md の「読んでいないコードは変更するな」「複雑なタスクでは十分に調査してから行動」を、CLI 更新という"簡単に見える"作業でも適用する。

### 2. npm 更新は稼働中プロセスを置き換えない（時限爆弾化する）

`npm install -g` は on-disk バイナリを差し替えるが、メモリ上で動いている旧プロセスはそのまま。「更新したのに今は動いている」を「成功」と誤認すると、次の再起動で壊れる。**プロセス起動時刻 vs 更新時刻の比較**と **watchdog ログ**で「今動いているのは新旧どちらか」を切り分けるのが有効だった。

### 3. 早期の自己点検が実害を防いだ

誤更新の直後に「記録を残す」目的で最近のジャーナルを読んだことが、退行の発見につながった。作業後にドキュメントへ立ち返る習慣が、結果的にセーフティネットになった。

### 検証 1: 既存 tracepatched APK

対象: `~/Desktop/walkman-tracepatched-resigned.apk`

- SHA256: `821e8522d02d76a3c8ac81d00e755c56966ee2f0bfc448f6c2685ac86919eaa7`
- Android 9 (`wmtest`) で `adb install -r -d` は **Success**
- 起動直後にクラッシュ:

```text
java.lang.RuntimeException: Unable to create application com.sony.walkman.highresmediaplayer.HighResMediaPlayerApp: java.util.NoSuchElementException
Caused by: java.util.NoSuchElementException
  at android.os.HwBinder.getService(Native Method)
```

結論: install 可能だが、Sony 固有の `IzmProperties` HIDL service がない通常 Android エミュレータでは起動不可。

### 追加パッチ

`apktool` で smali 展開し、以下を追加パッチ:

- `com/sony/walkman/izmproperties/IzmProperties.smali`
  - `connect()` を no-op false に変更
  - 未接続時の `get(key, default)` は default を返す
  - 未接続時の `set(...)` は no-op
- `com/sony/walkman/highresmediaplayer/model/properties/IzmPropertiesWrapper.smali`
  - highres 側 `connect()` を no-op
  - body color / destination / model id / 40th anniversary 判定を未接続時 default 返却へ変更
- `com/sony/songpal/localplayer/playbackservice/WmPlayer.smali`
  - APK に `lib/` native `.so` が入っていないため、`nativeInit()` など WmPlayer native methods を 0 返却 stub に変更
- `com/sony/walkman/soundeffectapp/model/properties/IzmPropertiesWrapper.smali`
  - soundeffect 側も未接続時 default / no-op へ変更

成果物:

- `~/Desktop/walkman-macemu-patched.apk`
- SHA256: `0a6725f92f6ee3240fe0d420d7076dc64671445e8a8147e8bc7e5750fa1ad2f2`
- 署名: debug keystore、APK Signature Scheme v3 で verify OK

### 検証 2: Android 9 / API 28

`wmtest` (Android 9 / arm64) で patched APK は install 成功。ただし起動時に AndroidX が Android 10+ API を呼んで落ちる:

```text
java.lang.NoSuchMethodError:
No virtual method registerActivityLifecycleCallbacks(Landroid/app/Application$ActivityLifecycleCallbacks;)V in class Landroid/app/Activity
  at androidx.lifecycle.ReportFragment$LifecycleCallbacks.registerIn(ReportFragment.java:167)
```

結論: `minSdk 28` に下げても、現状 APK は Android 9 では runtime API 不足で起動不可。Android 9 対応を本当に狙うなら AndroidX lifecycle 側の互換パッチが追加で必要。

### 検証 3: Android 14 / API 34

`wmtest34` (Android 14 / arm64) で `walkman-macemu-patched.apk` を install → 起動。

- `topResumedActivity=... com.sony.walkman.highresmediaplayer/.activity.MainActivity`
- `pidof com.sony.walkman.highresmediaplayer` = PID 2880

### 現時点の結論

- Mac ローカル Android Emulator 検証環境は構築済み。
- Android 14 では `walkman-macemu-patched.apk` が **MainActivity まで起動成功**。
- Android 9 では install は成功するが、AndroidX lifecycle の API 不足で起動不可。
- native `.so` が APK 内に存在しないため、今回の APK は **UI 起動確認用の stub パッチ**。音楽再生機能は未検証で、WmPlayer native 処理は実装ではなく no-op。
- 検証後、エミュレータは `adb emu kill` で停止済み。
