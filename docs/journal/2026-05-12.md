## 学んだこと / 気づき

### 1. 「軽い処理に見えて重いプロセス」の検知法

top の RSS だけでは瞬間サンプルアーティファクトに騙される (Reco 1150 MB → 実 111 MB)。 確定には以下を組み合わせる:

- `ps -p <PID> -o rss,etime` で複数回
- `sample <PID> 2` で stack 取得 (idle なら `_BlockUntilNextEventMatchingListInMode` で時間が止まる)
- `lsof -p <PID>` でファイル/ネットワーク活動
- システムログ / クラッシュレポート / アプリログを並行

### 2. WhisperKit ANE 変換は初回 5〜15 分かかる

CoreML mlmodelc → Apple Neural Engine bnnsir コンパイルが初回必要。
- 1.8 GB の TextDecoder で 1.2 GB の bnnsir が生成される
- top の CPU は ANE を映さないので idle に見えるが、 ANE は裏でフル稼働
- 進捗の判定は `com.apple.e5rt.e5bundlecache/` のサイズ増加 + ネット接続ゼロ確認

### 3. Reco の Ollama API シーケンス完全把握 (将来再利用可)

Reco は Ollama 互換 API を以下の順で叩く:

1. `GET /api/tags` (起動時の検出 + 完了確認)
2. `GET /api/version` (バージョン取得)
3. `POST /api/pull` (モデル DL、stream で `{"status": "pulling..."}` 系を受信)
4. `POST /v1/chat/completions` ← **OpenAI 互換ルート、`/api/chat` ではない**

`/v1/chat/completions` の使用は **Reco 固有の選択** (Ollama は両方サポート、Reco 開発者が OpenAI SDK 系を使っていた可能性)。

### 4. Reco の system prompt 完全可視化

mock の POST body ロギングで Reco が Gemma 4 に投げる system prompt 全文取得。 これは Reco の AI 要約の「ブランド」そのもの:
- 「達成感と前進が伝わる記録」
- 「動かしたもの」の 4 軸 (アウトプット / タスク前進 / アイデア / コミュニケーション)
- 「今日の状態」「今後やりたいこと」
- 動詞で終わる文 (体言止め禁止)
- 200〜400 字

→ もし仲氏が同等の voice journal 機能を Claude で自作するなら、 この prompt を流用できる。 ただし Claude のほうがプロンプト改造の柔軟性が圧倒的に高いので、流用する価値は限定的。

### 5. 🚨 macOS 26.5 launchd の TCC 罠

`~/Desktop` / `~/Documents` / `~/Downloads` 内のスクリプトを LaunchAgent で起動すると **Operation not permitted (Errno 1)**:
- 原因: launchd は親 Terminal の TCC 認可を継承しない
- 解決: スクリプトを `~/Library/Application Support/<app>/` 等の TCC 保護外に置く
- 代替: System Settings → Privacy & Security → Full Disk Access に launchctl/python3 を追加 (大げさ)

今後 LaunchAgent から実行したいスクリプトは **最初から TCC 外に配置**するのが安全 (既存の masu-p-watch.sh は `~/Desktop/scripts/` だが、 LaunchAgent 経由で動いている事実 → 別途 macOS バージョンで TCC ルールが違うか、 シェルスクリプト経由なら抜け道がある可能性、 要検証)。

### 6. Ollama 互換 mock の軽量さ

Python 110 行・RSS 10 MB で本物の Ollama (4.6 GB) を完全に騙せる。 アプリ側の依存検出ロジックが「ネットワーク到達 + JSON フォーマット OK」の 2 段だけなら、 mock サーバは強力な「軽量化ツール」になる。
M1 8GB 司令塔モードと相性最高。

### 7. 推測ミスを 2 回した (記録)

- (a) Terminal 101.6% CPU を「真犯人」候補にした → 実際は瞬間スパイク
- (b) 「エラー無し」と最初に断言 → UI エラーバナーを subsystem 検索で取りこぼした (ユーザー指摘で判明)

教訓: **画面のスクショ確認は早めにする** + **ログ調査は subsystem だけでなく unified log の generic タグや UI 描画系も見る**。
